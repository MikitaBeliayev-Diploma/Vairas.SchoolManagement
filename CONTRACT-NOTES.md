# School implementation alignment

Source hashes are recorded in source-manifest.json. Documentation/Database/school-management provides the thirteen-table canonical schema; Documentation/Communication/Api/school-management.openapi.yaml provides the canonical nine API operations. D-045 design documents supply invitation policy and replay/activation semantics. These inputs describe designs; this service's OpenAPI and validation report describe implemented behavior.

- Canonical HTTP routes and operation IDs are retained. The versioned /api/v1 and /internal/v1 prefixes and Idempotency-Key match the existing Auth/UM implementation; the D-045 prose's short routes and Operation-Id are not introduced as conflicting aliases.
- D-045 invitation routes are added under /api/v1/schools/{schoolId}/invitations and /api/v1/users/me/invitations. MutationResponse exposes the typed current resource and a replay flag. Accepted results retain the canonical accepting operation ID.
- Existing POST /internal/v1/profile-provisioning/validate echoes actorUserId/targetUserId/schoolId/invitationId/role/bootstrap and returns allowed/authorityBasis/validUntil. It is local-only and has no callback into UM. It never consumes an invitation.
- The current UM staff-provisioning contract does not return/check the proposed richer issuer UserId/activity basis. This implementation does not alter UM's API. School acceptance separately checks issuer activity and school authority before local staff reuse; a global role profile grants no school rights.
- Operator configuration uses canonical UM UserIds. Bootstrap validation is read-only and requires configured operator, Administrator role, existing active school and no effective Administrator membership. It does not activate the first membership.
- All eligibility-changing mutations remain unavailable before effects until a verified Scheduling gate exists. There are no fake queued operations, 202 responses, automatic retries, compensations or calendar-derived substitutes. No gate is claimed resolved.
- Enrollment category catalogue, pinned programme and completion evidence remain outside School ownership. No legal category list, hours, readiness logic or grant-management policy is invented.
- group_roster_revision and group_roster_member are append-only. Exact historical revision/interval reads never rewrite or substitute current evidence. Current operational reads fail closed on unresolved coordinated operations.
- The canonical DDL is frozen unchanged. The exclusion SQL has only its standalone BEGIN/COMMIT wrappers removed for the EF transaction. Implementation additions are immutable-evidence/invitation/operation triggers and a narrow SECURITY DEFINER self-discovery function; no additional domain tables.
- Initial migration is for an empty database. This is not an upgrade migration for an unknown existing production schema. Runtime grants/RLS are applied explicitly by the migration owner; runtime never owns tables. The trusted application may set a school GUC after resolving its actor and checking local authority; RLS protects omitted predicates, not a compromised service deliberately forging trusted scope.
- Structured logs contain method, route template, response status, duration, correlation ID and safe failure code/type. Audit operations retain actor/binding/outcome without credentials or full payloads.
- No MCP mutation delegation, Azure Service Bus inbox/outbox, SMTP, Learning or Scheduling service implementation is added. No source Documentation or neighboring service source is changed.
